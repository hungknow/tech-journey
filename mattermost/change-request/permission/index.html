Permission: Server and Frontend

This document describes how permissions are enforced on the server, what the frontend receives on failure, and how the frontend consumes permissions to show or hide features.

Server

How permission is checked

Permission is not enforced by a single middleware. Each API handler is responsible for checking permission after the request is authenticated. Handlers are registered with APISessionRequired (or similar) so that the session is loaded first; then inside the handler the code calls the app’s permission helpers and, on failure, sets the context error.

The check always runs in the context of the current request: the session is taken from c.AppContext.Session(), and the handler has access to URL/body params (e.g. userId, channelId, teamId, postId). Permission is evaluated per request, per resource (user, team, channel, etc.) when relevant.

Helpers (in server/channels/app/authorization.go):

  • SessionHasPermissionTo(session, permission) — System-level: does the session’s user have this permission via their system roles? Unrestricted sessions (e.g. local) are allowed. Implemented by resolving the session’s roles and calling RolesGrantPermission(roleNames, permissionId).
  • SessionHasPermissionToTeam(session, teamID, permission) — Team-level: system roles first; if not granted, then the user’s membership and roles in that team. System admin can still grant.
  • SessionHasPermissionToChannel(rctx, session, channelID, permission) — Channel-level: loads channel and channel membership; checks channel roles, then system admin, then team-level permission for that channel’s team. Returns (hasPermission, isMember) for auditing.
  • SessionHasPermissionToUser(session, userID) — Own user always; otherwise requires EditOtherUsers (and cannot act on system admins unless caller is system admin).
  • SessionHasPermissionToUserOrBot(rctx, session, userID) — Used for “act on this user/bot” (e.g. get/update user); combines bot management permission and user permission.
  • SessionHasPermissionToChannelByPost(session, postID, permission) — Resolves channel from post, then channel membership roles or team permission.
  • SessionHasPermissionToGroup(session, groupID, permission) — Custom group membership and system roles.
  • HasPermissionToChannel(rctx, askingUserId, channelID, permission) — Same logic as channel permission but by user id (used when the “actor” is not the current session, e.g. background jobs).

RolesGrantPermission(roleNames, permissionId) loads roles by name, skips deleted roles, and returns true if any role’s Permissions slice contains the given permission id. This is the core “do these roles grant this permission?” check used by all session/team/channel helpers.

Example: RolesGrantPermission(["team_user", "team_admin"], "manage_channel") → loads roles by names; if team_admin has Permissions: [..., "manage_channel", ...], returns true. Role from cache might look like { Name: "team_admin", Permissions: ["manage_channel", "delete_channel", "add_user_to_team", ...] }.

Setting the error. When a handler decides the session lacks permission, it calls c.SetPermissionError(permission(s)). That is implemented in server/channels/web/context.go as c.Err = model.MakePermissionError(c.AppContext.Session(), permissions).

MakePermissionError (in server/public/model/permission.go) builds an AppError with:

  • Id: "api.context.permissions.app_error"
  • StatusCode: http.StatusForbidden (403)
  • DetailedError: string that includes userId= and permission= (or comma-separated list of permission ids)

Example DetailedError when one permission was missing: userId=8x7y6z5a4b3c2d1e0f permission=manage_channel. When multiple: userId=8x7y6z5a4b3c2d1e0f permission=manage_channel,delete_channel.

The detailed error and the specific permission(s) passed to SetPermissionError are what distinguish which permission was missing.

What error is returned to the frontend

When c.Err != nil, the handler does not write a success body. The error is handled in handleContextError (in server/channels/web/handlers.go). For API calls (and webhook / mobile requests), the response is JSON and the status code is c.Err.StatusCode.

AppError JSON (from AppError.ToJSON() in server/public/model/utils.go) includes:

  • id — e.g. "api.context.permissions.app_error" for permission errors
  • message — translated user-facing message (e.g. “You do not have the appropriate permissions.” for api.context.permissions.app_error in server/i18n/en.json)
  • detailed_error — server-side details (e.g. userId=... permission=...); may be cleared in non-developer mode
  • request_id
  • status_code — 403 for permission errors

Example response body (permission error):

{
  "id": "api.context.permissions.app_error",
  "message": "You do not have the appropriate permissions.",
  "detailed_error": "userId=8x7y6z5a4b3c2d1e0f permission=manage_channel",
  "request_id": "abc1def2ghij3klm",
  "status_code": 403
}

The frontend can treat 403 as “forbidden” and use id or status_code to show a generic or specific message (e.g. permission vs. other forbidden cases).

Audit. When the context error is set and an audit record is logged, permission errors are recognized by c.Err.Id == "api.context.permissions.app_error" and logged at a dedicated “perms” level (LevelPerms) in LogAuditRecWithLevel.

In-memory data for fast permission checks

The server keeps permission-related data in memory so that the helper functions can resolve team, channel, and post permissions with minimal database access.

Session (request-scoped, with optional cache). When a request is authenticated, the handler gets a session. The session is either served from the platform session cache (keyed by token, TTL from SessionCacheInMinutes) or loaded from the store. In both cases the session object in memory already carries:

  • Roles — The user’s system role names (e.g. system_user, system_admin), stored on the session row and exposed as session.GetUserRoles().
  • TeamMembers — A slice of *model.TeamMember for all non-deleted teams the user belongs to. This is filled when the session is loaded from the store: SessionStore.Get() calls Team().GetTeamsForUser(userId) and attaches the result to the session. So once the session is in hand, team membership and team-level roles are in memory.

Example session data in memory:

  • session.Roles → "system_user" (or "system_user system_admin" for admin)
  • session.GetUserRoles() → ["system_user"]
  • session.TeamMembers → e.g. [{ TeamId: "team_abc", Roles: "team_user team_admin" }, { TeamId: "team_xyz", Roles: "team_user" }]
  • session.GetTeamByTeamId("team_abc") → that team member; GetTeamByTeamId("team_abc").GetRoles() → ["team_user", "team_admin"]

SessionHasPermissionToTeam therefore does not hit the store for team data: it uses session.GetTeamByTeamId(teamId) (a scan over the in-memory TeamMembers slice) and then RolesGrantPermission(teamMember.GetRoles(), permission.Id). The only possible store call in that path is RolesGrantPermission, which uses the role cache (see below).

Role cache (store layer). The local cache layer (server/channels/store/localcachelayer) wraps the store with in-memory caches:

  • roleCache — Key: role name. Value: *model.Role (includes Permissions slice). TTL 30 minutes. Used by RoleStore.GetByName and GetByNames. When RolesGrantPermission(roleNames, permissionId) calls GetRolesByNames, each role is read from this cache when present; only missing roles are loaded from the database and then stored in the cache.

Example: key "channel_user" → value { Id: "role_id_1", Name: "channel_user", Permissions: ["read_channel", "add_reaction", "upload_file", "edit_post", ...] }. Key "team_admin" → { Name: "team_admin", Permissions: ["manage_channel", "manage_team", "add_user_to_team", ...] }.

  • rolePermissionsCache — Key: sorted role names joined (e.g. for “channel higher scoped permissions”). TTL 30 minutes. Used for scheme-related permission resolution.

For system and team permission checks, the hot path is: session in memory (system roles + team members) → role names → role cache → permission id check. No DB hit if session was cached and roles are cached.

Channel: channel-by-id and all channel members for user. Channel permission needs the channel and the user’s channel memberships:

  • channelByIdCache — Key: channel id. Value: *model.Channel. TTL 15 minutes. Used by ChannelStore.Get(id, allowFromCache). SessionHasPermissionToChannel’s GetChannel(rctx, channelID) can be satisfied from this cache.

Example: key "chan_abc123" → value { Id: "chan_abc123", TeamId: "team_abc", Name: "general", Type: "O", ... }.

  • channelMembersForUserCache — Key: userId (and userId+"_deleted" when including deleted). Value: map[string]string (channel id → roles string for that channel). Size derived from SessionCacheSize, TTL 15 minutes. Used by ChannelStore.GetAllChannelMembersForUser(rctx, userId, true, includeDeleted). A single cache lookup returns the full map of channel id → roles for that user; the permission helper then picks the entry for the requested channel and calls RolesGrantPermission on those role names (again using the role cache).

Example: key "user_8x7y6z" → value { "chan_abc123": "channel_user", "chan_def456": "channel_user channel_admin", "chan_ghi789": "channel_user" }. For channel chan_def456, the helper gets role names ["channel_user", "channel_admin"] and calls RolesGrantPermission with that and the requested permission id.

For channel permission: one or two cache lookups (channel by id, all channel members for user) plus role cache for the channel’s role names. No DB if all are cached.

Post. SessionHasPermissionToChannelByPost and SessionHasPermissionToReadPost resolve the channel for the post and then check channel (or team) permission:

  • GetMemberForPost(postID, userId) — Returns the channel member for that post and user. There is no dedicated cache for this at the store layer; it hits the database (or underlying store). Example return: { ChannelId: "chan_abc123", UserId: "user_8x7y6z", Roles: "channel_user channel_admin", ... } (or error if not a member).
  • GetForPost(postID) — Returns the channel for the post. Also not cached at the store layer. Example return: { Id: "chan_abc123", TeamId: "team_abc", ... }.

For post permission the server may do a DB query to get the channel and/or the channel member for that post. After that, channel permission uses the same channel and channel-members caches as above; if the member was found, RolesGrantPermission still benefits from the role cache. Team fallback uses the in-memory session team members.

Team list cache (for other code paths). The store also has teamAllTeamIdsForUserCache (key: userId, value: list of team ids). That is used by TeamStore.GetUserTeamIds, not by the session’s TeamMembers. Example: key "user_8x7y6z" → value ["team_abc", "team_xyz"]. Session load uses GetTeamsForUser (full team members), which is not cached at the local cache layer; the session is then cached at the platform layer, so repeated requests with the same token reuse the same session with its in-memory TeamMembers.

Invalidation. When roles, channel membership, or team membership change, the relevant caches are invalidated (e.g. InvalidateAllChannelMembersForUser, InvalidateAllTeamIdsForUser, role/scheme cluster events, ClearSessionCacheForUser), so the next permission check loads fresh data and repopulates the cache.

Frontend

How permission is consumed

The frontend does not re-check permissions with the server on every click. It gets roles from the server and then derives permissions locally:

  • User and team memberships — Loaded at login / app load (e.g. getMe, getMyTeams, getMyTeamMembers). The current user’s roles string (system roles) and each team membership’s roles are stored in Redux.
  • Channel memberships — Loaded when switching team or loading channels (e.g. fetchChannelsAndMembers). Each channel member has a roles string; these are stored and used for channel-scoped permission.
  • Role definitions — Role names are collected from the user, team memberships, and channel memberships. loadRolesIfNeeded(roles) is called (e.g. after getMe and after fetchChannelsAndMembers) to fetch role details by name via Client4.getRolesByNames. The result is stored in state.entities.roles.roles (role name → role object with permissions array).

The frontend’s permission state is: current user’s system roles, current team’s membership roles, current channel’s membership roles, and the set of role definitions (with their permission ids) fetched when those roles are first needed.

Example Redux-style data:

  • Current user: users[currentUserId].roles → "system_user" (or "system_user team_user channel_user" depending on product).
  • Team membership: teamMembers[teamId][currentUserId].roles → "team_user team_admin".
  • Channel membership: channelMembers[channelId][currentUserId].roles → "channel_user" or "channel_user channel_admin".
  • Role definitions: state.entities.roles.roles → e.g. { channel_user: { id: "id1", name: "channel_user", permissions: ["read_channel", "add_reaction", "upload_file", ...] }, team_admin: { name: "team_admin", permissions: ["manage_channel", "manage_team", ...] }, ... }.

Selectors (in webapp/channels/src/packages/mattermost-redux/src/selectors/entities/roles.ts and roles_helpers.ts):

  • haveISystemPermission(state, { permission }) — True if the current user’s system roles (from getMySystemRoles) grant the given permission id.
  • haveITeamPermission(state, teamId, permission) — True if system roles grant it or the user’s roles in that team grant it.
  • haveIChannelPermission(state, teamId, channelId, permission) — True if system, team, or channel roles grant it.
  • haveICurrentTeamPermission(state, permission) — Convenience: haveITeamPermission(state, getCurrentTeamId(state), permission).
  • haveICurrentChannelPermission(state, permission) — Convenience: haveIChannelPermission(state, getCurrentTeamId(state), getCurrentChannelId(state), permission).

These selectors use the stored roles and the role definitions’ permissions arrays; they do not call the API. Consuming permission on the frontend means reading Redux state through these selectors or through permission gates that use them.

Example: haveIChannelPermission(state, "team_abc", "chan_def456", "add_reaction") → looks up system roles, then state.entities.teams.membersInTeam.team_abc[currentUserId].roles, then state.entities.channels.roles[chan_def456]; for each role set, checks whether the role definition’s permissions includes "add_reaction"; returns true if any scope grants it.

Displaying or hiding features by permission

Permission gates. The app uses wrapper components that conditionally render children based on a permission check. They all use the same Gate component: if the computed “hasPermission” (or its inverse when invert is true) is true, children are rendered; otherwise the gate renders nothing.

  • SystemPermissionGate — Uses haveISystemPermission for the given permission(s). If any of the permissions is granted, the gate passes. Used for system-wide actions (e.g. create team, manage system).
  • TeamPermissionGate — Uses haveITeamPermission for the given teamId and permission(s). Used for team-scoped actions (e.g. add user to team, invite guest).
  • ChannelPermissionGate — Uses haveIChannelPermission for the given teamId, channelId, and permission(s). Used for channel-scoped actions (e.g. add reaction, convert channel to public/private, delete post, manage channel bookmarks).

So “display by permission” = wrap the UI in the right gate; “hide by permission” = the same gate: when the user lacks permission, the gate renders nothing, so the feature is hidden.

Example: <ChannelPermissionGate channelId={currentChannel.id} teamId={currentTeam.id} permissions={[Permissions.ADD_REACTION]}><AddReactionButton /></ChannelPermissionGate> — if the user has add_reaction in the current channel (via system, team, or channel roles), the button is rendered; otherwise the gate returns null and the button is not shown.

Examples of display/hide by permission:

  • App bar / marketplace — “Open marketplace” in the app bar is shown only when marketplace is enabled and the user has SYSCONSOLE_WRITE_PLUGINS (via haveICurrentTeamPermission). The marketplace entry is hidden for users without that permission.
  • Sidebar — Create public/private channel and join public channel buttons use haveICurrentChannelPermission for CREATE_PUBLIC_CHANNEL, CREATE_PRIVATE_CHANNEL, JOIN_PUBLIC_CHANNELS. Custom groups creation uses CREATE_CUSTOM_GROUP with haveISystemPermission. Channel creation and join UI are shown only when the user has the right permission.
  • Team sidebar — “More teams” / create team is wrapped in SystemPermissionGate with CREATE_TEAM; users without it don’t see that option.
  • Select team / no open teams — Different messages and actions for users who have CREATE_TEAM vs. those who don’t (using SystemPermissionGate with and without invert). System console link is gated with MANAGE_SYSTEM.
  • Team members modal — Invite/add user is wrapped in TeamPermissionGate with ADD_USER_TO_TEAM and INVITE_GUEST so only users with at least one of these see the invite UI.
  • Channel header — Convert to public/private, manage channel access, and delete channel are wrapped in ChannelPermissionGate with the corresponding permissions so only users with the right channel (or team) permission see those menu items.
  • Post actions — Add reaction is behind ChannelPermissionGate with ADD_REACTION; burn-on-read delete and other post menu items are similarly gated so only users with the right channel permission see them.
  • Channel intro — “Add members” and “Create channel” CTAs are shown only when the user has MANAGE_PUBLIC_CHANNEL_MEMBERS / MANAGE_PRIVATE_CHANNEL_MEMBERS or CREATE_PUBLIC_CHANNEL etc., and invite is gated with INVITE_USER via TeamPermissionGate.
  • Dot menu / actions menu — Marketplace and plugin-related options are shown only when the user has SYSCONSOLE_WRITE_PLUGINS (and marketplace enabled); other options are gated by channel or system permission as appropriate.

Features are displayed when the user has the corresponding permission (via gates or direct selector checks) and hidden when they don’t—without a separate “hide” component; hiding is the default when the gate does not pass.

Handling server permission errors

If the frontend shows an action (e.g. user had permission at load time) and the user triggers it, the server can still return 403 (e.g. permission changed, or a bug). The frontend handles that like other API errors: it receives the JSON with status_code: 403 and id: "api.context.permissions.app_error". Some code paths branch on status_code === 403 (e.g. to show a “forbidden” or “no permission” message, or to treat notify-admin as already complete). The frontend both prevents showing actions the user shouldn’t see (via gates) and handles the case when the server denies the request with the standard permission error.
