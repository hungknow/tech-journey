MongoDB Collections for Query Acceleration

This document recommends which data from the Postgres-backed stores (see ../sql/) should be mirrored or denormalized in MongoDB to speed up read-heavy queries. Postgres remains the source of truth for writes; MongoDB is used as a read-optimized cache or materialized view.

1. Rationale

Goal How MongoDB helps
Channel timeline Single-document or indexed reads by channelId + createAt / updateAt instead of JOINs and reply-count subqueries.
Thread view Posts by rootId with optional embedded thread metadata (reply count, participants).
Sidebar / unreads Denormalized “user → channels with unread” or “channel → member summary” to avoid repeated ChannelMembers + Channels + Posts joins.
Post + reactions + files Embed or co-locate reactions and file metadata with post docs to serve timeline in one round-trip.
Search Atlas Search or text index on message content; filter by allowed channel IDs without heavy Postgres FTS + channel subqueries.
User preferences / drafts Document per user (or per user+team) for “get all prefs” or “get all my drafts” in one read.

When to keep reads on Postgres only: Strong consistency requirements, complex multi-table transactions, or tables that are write-heavy and rarely read (e.g. audit, jobs, compliance). This doc calls out such cases.

2. Recommended MongoDB Collections

2.1. posts (mirror + denormalized fields)

Source: Postgres Posts (and optionally Threads for collapsed-threads).

Purpose: Speed up:

  • Channel timeline: root posts by (channelId, deleteAt, createAt) with pagination.
  • “Posts since” by (channelId, updateAt).
  • Single post by id; thread replies by rootId.
  • Optional: embed replyCount, lastReplyAt, participants, following for collapsed threads so the app avoids JOINs with Threads and ThreadMemberships.

Document shape (minimal mirror):

{
  "_id": "<postId>",
  "channelId": "...",
  "rootId": "",
  "userId": "...",
  "message": "...",
  "type": "",
  "createAt": 1234567890,
  "updateAt": 1234567890,
  "deleteAt": 0,
  "editAt": 0,
  "isPinned": false,
  "props": {},
  "hashtags": "",
  "filenames": "",
  "fileIds": "",
  "hasReactions": false,
  "originalId": "",
  "remoteId": ""
}

Optional denormalized (collapsed threads):

  • replyCount, lastReplyAt, participants (array of user ids), following (bool per requesting user — usually not stored in post doc; keep in a separate view or resolve at read time).

Indexes:

Index Purpose
{ channelId: 1, deleteAt: 1, createAt: -1 } getRootPosts, GetPostsBefore/After, paginated timeline
{ channelId: 1, updateAt: -1 } GetPostsSince, GetEtag
{ rootId: 1, deleteAt: 1, createAt: 1 } GetPostsByThread, thread replies
{ _id: 1 } Get (single post), GetPostsByIds
{ userId: 1 } PermanentDeleteByUser / sync invalidation

Sync: Dual-write from app on Postgres Save/Update/Delete (and thread updates), or CDC from Postgres (e.g. Debezium) into a worker that upserts/deletes in MongoDB. On conflict, Postgres wins; MongoDB is eventually consistent.

Postgres-only: Save, Update, Delete, PermanentDelete*, search (unless you add a dedicated search collection), analytics (materialized views), export/sync batches. Use Postgres for any path that must see uncommitted data.

2.2. post_reactions (by post)

Source: Postgres Reactions.

Purpose: GetForPost, GetForPosts (batch) — avoid extra round-trips when rendering timeline.

Document shape (one doc per post):

{
  "_id": "<postId>",
  "reactions": [
    { "userId": "...", "emojiName": ":emoji:", "createAt": 1234567890 }
  ],
  "updateAt": 1234567890
}

Indexes:

Index Purpose
{ _id: 1 } Lookup by postId (GetForPost, batch GetForPosts)

Sync: On Reaction Save/Delete in Postgres, update or replace the post_reactions doc for that postId. Optional: maintain from posts + reactions via CDC.

Alternative: Embed reactions array inside each posts document. That simplifies reads but forces post doc updates on every reaction change; acceptable if reaction volume is moderate and you already dual-write posts.

2.3. post_files (file metadata by post)

Source: Postgres FileInfo.

Purpose: GetForPost, GetByIds — show file list with post without a second query.

Document shape (one doc per post):

{
  "_id": "<postId>",
  "files": [
    {
      "id": "<fileId>",
      "name": "...",
      "extension": "...",
      "size": 123,
      "mimeType": "...",
      "createAt": 1234567890,
      "width": 0,
      "height": 0,
      "hasPreviewImage": false
    }
  ],
  "updateAt": 1234567890
}

Indexes:

Index Purpose
{ _id: 1 } Lookup by postId

Sync: On FileInfo Save/AttachToPost/DeleteForPost/PermanentDeleteForPost, update the post_files doc for the post. Can be driven by same CDC or app dual-write as posts.

Postgres-only: GetByPath, GetForUser (by creator), GetWithOptions (admin listing), PermanentDelete*, content storage.

2.4. channel_timeline (optional denormalized view)

Source: Postgres Posts + Threads (and optionally ChannelMembers for “following”).

Purpose: One read for “channel root posts with thread summary” (e.g. collapsed-threads UI) without JOINs.

Document shape (one doc per channel “page” or single doc with array of recent root post summaries):

Option A — one doc per channel with embedded recent root posts:

{
  "_id": "<channelId>",
  "lastPostAt": 1234567890,
  "lastRootPostAt": 1234567890,
  "totalMsgCount": 100,
  "totalMsgCountRoot": 50,
  "roots": [
    {
      "id": "<postId>",
      "userId": "...",
      "message": "...",
      "createAt": 1234567890,
      "updateAt": 1234567890,
      "replyCount": 3,
      "lastReplyAt": 1234567891,
      "participants": ["userId1", "userId2"]
    }
  ],
  "updateAt": 1234567890
}

Option B — keep posts collection only and use indexes above; no separate channel_timeline (simpler sync, same indexes as in 2.1).

Recommendation: Prefer a single posts collection with good indexes (2.1) unless you need a true “pre-aggregated” channel doc (e.g. fixed-size sliding window of recent roots). If you add channel_timeline, sync it from Postgres on post save/delete and thread updates.

2.5. user_channels (sidebar / unreads)

Source: Postgres Channels + ChannelMembers (+ optionally last post / unread from Posts/counts).

Purpose: GetChannelsByUser, GetChannelCounts, GetChannelsWithUnreadsAndWithMentions, GetChannelUnread — single read for sidebar and unread badges.

Document shape (one doc per user):

{
  "_id": "<userId>",
  "channels": [
    {
      "channelId": "...",
      "teamId": "...",
      "displayName": "...",
      "name": "...",
      "type": "O",
      "lastViewedAt": 1234567890,
      "msgCount": 10,
      "msgCountRoot": 5,
      "mentionCount": 0,
      "mentionCountRoot": 0,
      "totalMsgCount": 100,
      "totalMsgCountRoot": 50,
      "lastPostAt": 1234567891,
      "notifyProps": {}
    }
  ],
  "updateAt": 1234567890
}

Indexes:

Index Purpose
{ _id: 1 } Get all channels for user

Sync: On ChannelMembers Save/Update (including LastViewedAt, MsgCount, MentionCount) and on Channels update (LastPostAt, TotalMsgCount, etc.), update the corresponding user_channels doc(s). High write fan-out (one channel update touches many user docs); consider async worker or CDC.

Postgres-only: Channel CRUD, GetMember, GetMembers, scheme roles, permission checks. Use Postgres for consistency when membership or roles change.

2.6. users (profile cache)

Source: Postgres Users.

Purpose: Get, GetMany, GetProfileByIds — reduce load on Postgres for profile-by-id lookups (e.g. when rendering posts).

Document shape (subset for display):

{
  "_id": "<userId>",
  "username": "...",
  "nickname": "...",
  "firstName": "...",
  "lastName": "...",
  "email": "...",
  "createAt": 1234567890,
  "updateAt": 1234567890,
  "deleteAt": 0,
  "lastPictureUpdate": 0,
  "locale": "...",
  "roles": "...",
  "notifyProps": {}
}

Indexes:

Index Purpose
{ _id: 1 } Get by id
{ username: 1 } GetByUsername (optional)
{ email: 1 } GetByEmail (optional)

Sync: Dual-write or CDC on User Save/Update/Delete. TTL or event-driven invalidation if you use MongoDB only as cache.

Postgres-only: Auth (password, AuthData), Search/Autocomplete (unless you mirror for search), PermanentDelete, sensitive fields. Prefer Postgres for any path that must see latest roles/permissions.

2.7. user_preferences

Source: Postgres Preferences.

Purpose: Get, GetCategory, GetAll — one read for “all preferences for user” or “category for user”.

Document shape (one doc per user):

{
  "_id": "<userId>",
  "prefs": [
    { "category": "flagged_post", "name": "<postId>", "value": "true" },
    { "category": "display_settings", "name": "theme", "value": "default" }
  ],
  "updateAt": 1234567890
}

Alternative: nested by category:

{
  "_id": "<userId>",
  "display_settings": { "theme": "default", ... },
  "flagged_post": { "<postId>": "true", ... },
  "updateAt": 1234567890
}

Indexes:

Index Purpose
{ _id: 1 } Get by userId

Sync: On Preference Save/Delete/PermanentDeleteByUser, update the user’s doc. Low write volume.

Postgres-only: GetCategoryAndName (by category+name across users), DeleteCategoryAndName (global). Use Postgres when you need cross-user preference queries.

2.8. user_drafts

Source: Postgres Drafts.

Purpose: GetDraftsForUser — one read for “all my drafts” (with optional team filter in app).

Document shape (one doc per user):

{
  "_id": "<userId>",
  "drafts": [
    {
      "channelId": "...",
      "rootId": "",
      "message": "...",
      "fileIds": [],
      "createAt": 1234567890,
      "updateAt": 1234567890,
      "props": {},
      "priority": "",
      "type": ""
    }
  ],
  "updateAt": 1234567890
}

Indexes:

Index Purpose
{ _id: 1 } Get drafts for user

Sync: On Draft Upsert/Delete/DeleteDraftsAssociatedWithPost, update the user’s doc. Low volume.

Postgres-only: Get (single draft by user+channel+root), migration. Use Postgres when you need a single-draft lookup by (UserId, ChannelId, RootId) if you don’t query by user often.

2.9. post_search (optional — dedicated search collection)

Source: Postgres Posts (+ channel allow-list from app or a separate sync).

Purpose: Replace or complement Postgres full-text search (search, SearchPostsForUser) with MongoDB Atlas Search or text index; filter by channelId IN (allowedIds) and date/user without heavy JOINs.

Document shape:

{
  "_id": "<postId>",
  "channelId": "...",
  "teamId": "...",
  "userId": "...",
  "message": "...",
  "createAt": 1234567890,
  "deleteAt": 0,
  "type": "..."
}

Indexes:

Index Purpose
Atlas Search text index on message Full-text search
{ channelId: 1, createAt: -1 } Filter by channel, sort by time
{ deleteAt: 1, type: 1 } Exclude deleted / system

Sync: Same as posts; can be the same collection with a text index, or a dedicated search projection. Access control (allowed channel IDs) must be enforced at query time from Postgres or a cached membership store.

Postgres-only: Search that must see uncommitted posts or complex buildSearchPostFilterClause logic until you fully replicate that in the app.

3. What to Keep in Postgres Only

  • Writes: All inserts/updates/deletes originate in Postgres; MongoDB is a read mirror or cache.
  • Stores that are write-heavy or need strong consistency: Audit, Compliance, Jobs, Sessions, Tokens, OAuth, License, System, NotifyAdmin, RetentionPolicy, Scheme, Bot, Command, Webhook, Plugin, etc. No need to mirror in MongoDB unless you have a specific read-heavy endpoint that would benefit.
  • Complex transactions: e.g. Save post + update Channel + update Threads + FileInfo; run in Postgres; then async sync to MongoDB.
  • Analytics / reporting: Materialized views (posts_by_team_day, etc.), AnalyticsPostCount*, AnalyticsUserCountsWithPostsByDay — keep in Postgres (or move to a dedicated analytics DB; not “MongoDB for Mattermost reads”).
  • Export / sync / indexing batches: GetPostsBatchForIndexing, GetParentsForExportAfter, etc. can stay Postgres; optionally feed from Postgres into MongoDB or search index in a pipeline.

4. Sync Strategy (Summary)

Approach Pros Cons
Dual-write (app) Simple, immediate consistency for your writes Every write path must emit to MongoDB; risk of drift if a path is missed.
CDC (e.g. Debezium) Single source of truth in Postgres; no app code in write path Operational complexity; eventual consistency; must handle schema and deletes.
Batch job Simple, no change to write path Stale reads; only good for non–real-time views.

Recommendation: Start with dual-write for the hottest read paths (posts, post_reactions, post_files, optionally user_channels and user_preferences). Use a small abstraction (e.g. “MongoWriter”) so you can switch to CDC later. Keep Postgres as source of truth; on any inconsistency, Postgres wins and you can rebuild MongoDB from Postgres if needed.

5. Query Mapping (Where to Read)

API / Store function Prefer read from
Get (single post), GetSingle MongoDB posts by _id (fallback Postgres)
getRootPosts, GetPosts (channel timeline) MongoDB posts by channelId + deleteAt + sort by createAt (fallback Postgres)
GetPostsSince MongoDB posts by channelId + updateAt (fallback Postgres)
GetPostsByThread MongoDB posts by rootId + deleteAt (fallback Postgres)
GetForPost (reactions) MongoDB post_reactions by _id (fallback Postgres)
GetForPost (files) MongoDB post_files by _id (fallback Postgres)
GetChannelsByUser, GetChannelCounts, GetChannelsWithUnreadsAndWithMentions MongoDB user_channels by _id (fallback Postgres)
GetProfileByIds MongoDB users by _id (fallback Postgres)
GetCategory / GetAll (preferences) MongoDB user_preferences by _id (fallback Postgres)
GetDraftsForUser MongoDB user_drafts by _id (fallback Postgres)
Search / SearchPostsForUser MongoDB post_search with Atlas Search or text index (fallback Postgres FTS)

Implement a read-through pattern: try MongoDB first; on miss or error, use Postgres and optionally backfill MongoDB for the next time.
