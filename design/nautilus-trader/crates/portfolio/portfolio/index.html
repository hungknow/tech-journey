Portfolio Crate Documentation

Purpose

The nautilus-portfolio crate provides comprehensive portfolio management and risk analysis capabilities for the NautilusTrader trading system. It serves as the central component for tracking and calculating portfolio state, including real-time position management, performance metrics, and risk calculations.

Problem It Resolves

The portfolio crate addresses several critical challenges in algorithmic trading systems:

  1. Real-time Portfolio Tracking: Maintaining an accurate, up-to-date view of portfolio state across multiple accounts, venues, and instruments as trading events occur in real-time.

  2. Complex PnL Calculations: Computing accurate profit and loss metrics for both open (unrealized) and closed (realized) positions, including handling of partial fills, position cycling, and multi-venue scenarios.

  3. Multi-currency Support: Managing portfolios across different settlement currencies with automatic conversion and exposure analysis.

  4. Margin Management: Calculating and tracking initial margin requirements (for open orders) and maintenance margin requirements (for open positions) across different account types.

  5. Account State Synchronization: Keeping account balances, locked funds, and margin requirements synchronized with order lifecycle events.

  6. Order Management System (OMS) Variations: Supporting both NETTING and HEDGING OMS models with appropriate position and PnL accounting.

  7. Price Resolution: Implementing a hierarchical price resolution strategy for mark-to-market valuations.

Techniques Used

The portfolio crate employs several sophisticated techniques to solve these problems:

  1. Event-Driven Architecture: The portfolio subscribes to and processes various event types (OrderEventAny, PositionEvent, AccountState, QuoteTick, Bar, MarkPriceUpdate) through a message bus system, enabling reactive updates.

  2. Incremental State Caching: Realized PnL is cached incrementally from position snapshots, only processing new snapshots and detecting cache invalidation (purge/reset) to avoid unnecessary deserialization.

  3. NETTING OMS PnL Calculation: A three-case rule for position cycles:

  4. Active positions: Use only the last snapshot PnL
  5. Closed positions: Use sum of all snapshot PnLs

  6. Current realized PnL from active positions is added

  7. Hierarchical Price Resolution: Prices are obtained in priority order:

  8. Mark prices (if configured)
  9. Bid/ask prices based on position side (long→bid, short→ask)
  10. Last trade prices

  11. Bar close prices (if configured)

  12. Currency Conversion: Automatic conversion using exchange rates with configurable sources (quote vs. mark prices) and per-account base currency conversion.

  13. Rc<RefCell<>> Pattern: Shared state management allowing multiple references to the same portfolio state while ensuring thread-safe access through Rust's ownership system.

  14. Message Bus Integration: Typed handlers are registered for different event types, with both endpoint (direct) and topic (pub/sub) subscription patterns.

  15. Position Folding: For maintenance margin calculations, open positions are folded into a NETTING-equivalent state using quantity-weighted average prices.

  16. Timer-based Snapshotting: Periodic portfolio snapshots are emitted at configurable intervals while positions are open, with automatic timer management (arm/disarm based on position count).

  17. Throttled Logging: Account state logging can be throttled based on minimum interval settings to reduce log volume in high-frequency scenarios.

Data Flow

The data flow through the portfolio system follows a reactive event-driven pattern:

  1. External Event Sources: Trading events are generated by the execution engine and published to the message bus:
  2. Order events (accepted, filled, canceled, etc.)
  3. Position events (opened, changed, closed, adjusted)
  4. Account state events

  5. Market data (quotes, bars, mark prices)

  6. Message Bus Subscriptions: The Portfolio registers typed handlers for specific message patterns during initialization:

  7. events.order.* → Order updates
  8. events.position.* → Position updates
  9. events.account.* → Account state updates
  10. data.quotes.* → Quote tick updates
  11. data.bars.*EXTERNAL → Bar updates (if configured)

  12. data.mark_prices.* → Mark price updates (if configured)

  13. Event Processing: Each handler processes its event type:

  14. Order events (update_order):

    • For fills: Update balances, calculate unrealized PnL, recalculate order margins
    • For state changes: Recalculate initial margins for open orders
    • Generate and publish AccountState events

  15. Position events (update_position):

    • Update net position tracking
    • Recalculate unrealized and realized PnL
    • Update maintenance margins for margin accounts
    • Record closed position PnL for analysis

  16. Account state events (update_account):

    • Apply state to cache (if not already applied)
    • Throttled logging based on configuration

  17. Market data (update_quote_tick, update_bar, update_instrument_id):

    • Invalidate cached PnL for affected instruments
    • Recalculate pending PnL if prices become available
    • Update bar close price cache

  18. Cache Persistence: Updated accounts and positions are persisted to the central Cache, which serves as the system's source of truth.

  19. Message Publication: Updated AccountState and PortfolioSnapshot events are published back to the message bus for downstream consumers.

  20. Query Operations: Portfolio queries (PnL, equity, exposure) retrieve data from the cache and calculate on-demand, using cached values when available.

Logic Flow

The core portfolio logic flow operates through initialization, event processing, and query phases:

Initialization Phase

  1. Portfolio Creation: Portfolio::new() creates a new portfolio with:
  2. Shared Cache and Clock references
  3. PortfolioConfig with behavioral settings
  4. Internal PortfolioState with empty tracking structures

  5. Message bus handler registrations

  6. Order Initialization (initialize_orders):

  7. Scans cache for all open orders
  8. Groups by instrument
  9. Calculates initial margins using AccountsManager

  10. Updates accounts in cache

  11. Position Initialization (initialize_positions):

  12. Scans cache for all open positions
  13. Groups by instrument and calculates net positions
  14. Calculates initial unrealized and realized PnL
  15. Updates maintenance margins for margin accounts
  16. Arms snapshot timers if configured

Event Processing Loop

  1. Order Event Handling (update_order):
  2. Extract account ID and instrument
  3. Validate order lifecycle state
  4. For fills:
    • Update account balances (via AccountsManager)
    • Recalculate unrealized PnL
  5. Recalculate order margins
  6. Apply account state updates

  7. Publish AccountState (if not endpoint source)

  8. Position Event Handling (update_position):

  9. Update net position tracking
  10. Recalculate unrealized PnL using current market prices
  11. Recalculate realized PnL (may use snapshot data for NETTING OMS)
  12. Update maintenance margins for margin accounts
  13. Record closed position PnL for analysis

  14. Publish AccountState

  15. Market Data Updates:

  16. Invalidate cached PnL for affected instruments
  17. If PnL was previously pending and data is now available, recalculate

  18. Store bar close prices in cache

  19. Snapshot Timer Handling:

  20. Periodically emit PortfolioSnapshot events while positions are open
  21. Store snapshots in bounded buffer (1M entries)
  22. Automatically arm/disarm timers based on position count

Query Operations

  1. PnL Queries:
  2. Unrealized PnL: Calculate based on current market prices and open positions
  3. Realized PnL: Calculate using snapshot data (NETTING OMS) or direct aggregation (HEDGING OMS)

  4. Use cached values when available to avoid repeated calculations

  5. Equity Queries:

  6. Margin accounts: balance.total + unrealized PnL

  7. Cash accounts: balance.total + mark_values (notional values of open positions)

  8. Exposure Queries:

    • Calculate notional values of open positions
    • Convert to account base currency if configured
    • Aggregate per currency

  9. Position State Queries:

    • Net position: Sum of signed quantities across all open positions
    • Is net long/short/flat based on net position sign
    • Is completely flat: All instruments at zero net position

Account Management

  1. Balance Updates (via AccountsManager):

    • Apply PnL from fills
    • Deduct commissions
    • Handle currency conversion for multi-currency accounts
    • Support both single-currency and multi-currency balance updates

  2. Margin Calculations (via AccountsManager):

    • Initial margins: For open orders on each instrument
    • Maintenance margins: For net position exposure on each instrument
    • Support all instrument types (futures, options, crypto, betting, etc.)
    • Apply currency conversion as needed

  3. Account State Generation:

    • Generate AccountState events with current balances and margins
    • Include both per-instrument and account-wide margins
    • Apply throttled logging based on configuration
