Script and engine architecture

This document describes the business model of the script system: where candlestick data lives, how it is transferred and processed, how scripts interact with it, and how calculated indicators are stored and returned. The description is in plain language so the same design can be implemented in another framework or language.

Overview

The chart and its overlays run on the main thread (UI). Indicator logic runs in a separate execution context (e.g. a worker or another process). The two sides do not share memory: they communicate only by messages. The main thread owns the candlestick series and the list of overlays; when an overlay needs to be calculated, the main thread sends a message to run a script. The other side runs an engine that executes scripts bar by bar over the candlestick data it has received, then sends back the calculated series. So the flow is: chart/UI sends “run this script” and (if needed) “here is the data” → engine runs the script over the data → engine sends back “here are the results” → chart updates the overlay.

+---------------------------+         messages          +---------------------------+
|  MAIN THREAD (UI)         | <-----------------------> |  ENGINE (worker/process)   |
|                           |   "run script"            |                           |
|  - Chart                  |   "here is data"          |  - Copy of candlestick     |
|  - Candlestick series     |   "here are results"      |  - Script registry        |
|  - Overlay list           |   (no shared memory)      |  - Bar-by-bar loop        |
|  - Decides when to run    |                           |  - Only reacts to msgs    |
+---------------------------+                           +---------------------------+

Where candlestick data lives and how the chart uses it

The candlestick series is the primary series of the chart. It is stored in one place only: the main thread, as the chart’s main data. Each candle is one row: timestamp, open, high, low, close, and volume. The series is ordered by time (ascending) and has no duplicate timestamps. The chart and all main-thread logic read and write this single series. There is no separate “candlestick store”: the chart’s main data is the candlestick data. The engine does not hold this data by default; it receives a copy when the main thread sends it (see below).

How execution is triggered

The script (indicator) does not call the engine directly. User actions and UI lifecycle drive execution:

  • When an overlay that has a script is added or shown, the UI emits an event meaning “run the script for this overlay,” with a descriptor of the script (what to run, which pane, and any settings).
  • A central event handler listens for these events and turns them into outgoing messages to the engine: e.g. “run this one script” or “run all scripts,” plus current timeframe and visible range.
  • When the user changes a script setting (e.g. RSI period) or the visible range, the UI may send a message like “re-run only these overlays with these new settings.”

So the business rule is: the chart/UI decides when to run scripts and which scripts to run; the engine only reacts to messages. No direct call from script code to the engine.

How candlestick data is transferred to the engine

The engine runs in a separate context and has no direct access to the chart’s candlestick series. It can work with candlestick data only because the main thread sends it:

  • When the engine is about to run scripts, it may first announce: “I need candlestick data (OHLCV).” That is sent as a request-data message to the main thread.
  • The main thread responds by taking the chart’s primary candlestick series (the same one the chart draws), packaging it, and sending it in an upload-data message. So the engine receives a copy of the candlestick series at that moment. From then on, the engine’s copy is independent; the chart can keep updating its own series without the engine seeing those updates until the main thread sends another batch.
  • For live updates (e.g. new or updated candles in real time), the main thread can send an update-data message with only the new or changed candles. The engine then appends or updates the last bar(s) in its copy and re-runs the script for those bars only (incremental step).

So the transfer model is: pull on demand (engine says “I need data”) and push by the main thread (“here is the full series” or “here are the latest bars”). The engine never reads the chart’s memory; it only ever sees what was sent in messages.

  MAIN THREAD                    ENGINE
  -----------                    ------
  Candlestick series
       |                               |
       |  (1) request-data              |  "I need OHLCV"
       | <-----------------------------|
       |                               |
       |  (2) upload-data               |  (full copy of series)
       | ----------------------------->|
       |                               |
       |  (3) run script(s)             |  bar-by-bar loop
       | ----------------------------->|
       |                               |
       |  (4) overlay-data              |  (full or delta series)
       | <-----------------------------|
       |                               |
  Live: update-data (new bars) ------->|  incremental step
       overlay-update (new points) <---|

How the engine processes data: bar-by-bar loop

The engine holds:

  • A copy of the candlestick series (and optionally other datasets) that it received via messages.
  • A registry of scripts (one per overlay that has a script), each with its own small execution environment and settings.

To run scripts, the engine does a single pass over the candlestick series, bar by bar, in time order:

  • Before the loop: for each script, run its init phase once (setup).
  • For each bar:
  • Update internal rolling buffers that hold only the current bar and a short lookback (e.g. open, high, low, close, volume for the last few bars).
  • For each script, run its update phase once, passing that bar’s context (current and recent values). The script produces one output value (or a small tuple) for that bar.
  • Append that result to that script’s output series (the series that will later be drawn).
  • After the loop: for each script, run its post phase once (cleanup or finalization).

So the processing model is: one bar in, one value out per script per bar. Scripts do not iterate over the full history themselves; the engine drives the iteration and feeds each script only what it needs for the current bar (see next section). Optionally, a script depth setting can limit how many bars are processed (e.g. only the last N bars) to save time when the full history is not needed.

  ENGINE: bar-by-bar loop over candlestick copy
  ------
       +--------+
       |  init  |  once per script
       +--------+
            |
            v
  +---------+---------+---------+
  | Bar 1   | Bar 2   | Bar N   |  for each bar:
  +---------+---------+---------+    - update rolling buffers (open, high, low, close, vol)
       |         |         |       - for each script: update() -> one output value
       v         v         v       - append value to script output series
  [ out1 ]  [ out2 ]  [ outN ]
       |         |         |
       +---------+---------+
            |
            v
       +--------+
       |  post  |  once per script
       +--------+

How script code interacts with candlestick data

Scripts never see the “raw” full candlestick array. The engine gives them a sliding window of the current and recent past:

  • For each bar, the engine fills five short series: open, high, low, close, and volume. Each holds only the current bar at index 0 and a small number of previous bars (e.g. the last few). So “current close” is the first element, “previous close” is the second, and so on. Scripts (and built-in functions like EMA or RSI) read from these indices. This keeps memory bounded: the engine does not hand the script the entire history, only what is needed for lookback calculations.
  • Optionally, the script can be given read-only access to the full OHLCV series in the engine’s copy (e.g. for custom logic that needs arbitrary history). Most indicators do not need this; they only need the sliding window.
  • The script also receives current bar time, current bar index, timeframe, and visible range so it can align output with time.

Scripts are read-only on candlestick data. They write only their own output series (and optionally declare sub-overlays like extra lines). The engine collects those outputs and sends them back to the main thread (see below).

How calculated memory (e.g. RSI) is managed

Calculated indicators use two kinds of storage with different lifecycles:

Rolling buffers (bounded, for intermediate math)
- The engine’s price buffers (open, high, low, close, volume) are trimmed after each bar to a fixed small length (e.g. 5 or the script’s lookback). So memory for “current and recent bars” does not grow with the number of bars.
- Inside each script’s environment, intermediate series (e.g. the internal series used by an EMA or RSI formula) are also rolling: they have a maximum length (e.g. the indicator period or a small default). After each bar, the engine trims these to that length. So no matter how many bars are processed, the amount of memory per script for intermediate values stays constant. The exact length can be inferred from the indicator (e.g. RSI period) or set explicitly by the script.

Full-length output (what is drawn)
- Each script produces one output point per bar (e.g. one RSI value per bar). These points are appended to the script’s output series and are not trimmed. That full series—timestamp plus value for every bar—is what gets sent back to the main thread so the chart can draw the full indicator line. So: small rolling windows inside the engine for computation, full result series for display.

Worker-wide memory limit (optional)
- The engine can track total size of all datasets it holds (candlestick copy plus any other series). If a maximum size is configured, it can evict the least recently used dataset when over the limit, so total memory stays bounded. The candlestick copy is not special; it can be evicted and re-requested if needed.

  MEMORY INSIDE ENGINE (per script)
  --------------------------------
  ROLLING (bounded length, trimmed each bar):
  +------------------+     +------------------+
  | open, high, low  |     | intermediate     |
  | close, vol       |     | series (e.g.     |
  | (last few bars)  |     | EMA internal)    |
  +------------------+     +------------------+
         fixed length           fixed length

  FULL-LENGTH (sent back to chart, not trimmed):
  +----------------------------------------------+
  | output series: [ (t1,v1), (t2,v2), ... (tN,vN) ]  -> overlay data
  +----------------------------------------------+

How results are sent back to the chart

When the engine finishes a run (or an incremental update), it does not write into the chart’s memory. It sends outgoing messages:

  • Full run: a message carrying “overlay data” with the full calculated series for each script (and any sub-overlays). The main thread receives this and replaces the overlay’s data with the new series, then the chart redraws.
  • Incremental update: a message carrying only the latest point(s) for each overlay. The main thread merges these into the existing overlay data (e.g. append or update the last bar) so the chart can update without resending the full history.

The main thread may also receive engine state messages (e.g. “calculation started,” “calculation finished,” performance or data size). That is for UI feedback (e.g. loading flags), not for the data model.

So the result flow is: engine produces full or delta series → sends in message → main thread applies to overlay data → chart renders. The chart never reads the engine’s memory; it only updates from messages.

Summary (business model)

  • Candlestick storage: The chart keeps a single primary candlestick series on the main thread. The engine has no direct access; it works on a copy sent by the main thread via messages (full upload or incremental updates).
  • Triggering: The UI decides when to run scripts (overlay add/change, settings, range). It sends messages (“run script(s),” “here is data,” “re-run these with new settings”). The engine never initiates; it only responds to messages.
  • Transfer: Data flows main thread → engine by the main thread pushing the candlestick series (or deltas) in response to a data request. Results flow engine → main thread by the engine pushing full or incremental overlay series in messages.
  • Processing: The engine runs a bar-by-bar loop over its candlestick copy, maintains small rolling buffers of current and recent bars, and calls each script’s init once, update once per bar, and post once. Scripts read only from the sliding window (and optionally the full series); they write only their output series.
  • Memory: Rolling buffers (price buffers and intermediate indicator series) are trimmed to a fixed lookback so memory per script does not grow with bar count. Output series are full-length and sent back to the chart for drawing. An optional global size limit can evict least-recently-used datasets in the engine.

This model can be reimplemented in any framework or language by keeping the same roles (chart owns data and triggers; engine owns a copy and runs scripts; communication only by messages) and the same data flows and processing rules.
