Cython-Based CSV Data Processing

Overview

This document describes the data flow for processing CSV data into domain objects using the Cython-based implementation. This is the legacy approach that directly processes pandas DataFrames and creates Cython-wrapped C structs, providing efficient memory access through zero-copy memory views.

Architecture

┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌─────────────┐
│   CSV File  │ --> │   Pandas     │ --> │   Cython    │ --> │  C Structs  │ --> │  Python    │
│             │     │  DataFrame   │     │  Wrangler   │     │  (Bar_t)    │     │  Bar Objs  │
└─────────────┘     └──────────────┘     └─────────────┘     └─────────────┘     └─────────────┘

Data Flow

Step-by-Step Process

  1. CSV → DataFrame (Python) 

    df = pd.read_csv("data.csv", index_col="timestamp", parse_dates=True)
# Result: pandas DataFrame with columns [open, high, low, close, volume]

  2. DataFrame → Memory Views (Cython) 

    # Zero-copy views into numpy arrays
data.values      # double[:] memory view (5 columns: open, high, low, close, volume)
ts_events        # uint64_t[:] memory view (timestamps)
ts_inits         # uint64_t[:] memory view (initialization timestamps)

  3. Memory Views → Bar Objects (Cython) 

    return list(map(
    self._build_bar,
    data.values,    # double[:] - zero-copy view
    ts_events,      # uint64_t[:] - zero-copy view
    ts_inits        # uint64_t[:] - zero-copy view
))

  4. Bar Construction (Cython → Rust FFI) 

    cpdef Bar _build_bar(self, double[:] values, uint64_t ts_event, uint64_t ts_init):
    return Bar(
        bar_type=self.bar_type,
        open=Price(values[0], self.instrument.price_precision),      # Creates Price_t
        high=Price(values[1], self.instrument.price_precision),     # Creates Price_t
        low=Price(values[2], self.instrument.price_precision),       # Creates Price_t
        close=Price(values[3], self.instrument.price_precision),    # Creates Price_t
        volume=Quantity(values[4], self.instrument.size_precision), # Creates Quantity_t
        ts_event=ts_event,
        ts_init=ts_init,
    )

  5. C Struct Creation (Rust FFI) 

    // Called via FFI from Cython
Bar_t bar_new(
    BarType_t bar_type,
    Price_t open,
    Price_t high,
    Price_t low,
    Price_t close,
    Quantity_t volume,
    uint64_t ts_event,
    uint64_t ts_init
)

Memory Layout

C Struct Definitions

Price_t Structure (Standard Precision): 

typedef struct Price_t {
    int64_t raw;        // 8 bytes - fixed-point integer
    uint8_t precision;  // 1 byte - decimal precision
    // Padding: 7 bytes (aligned to 8-byte boundary)
} Price_t;  // Total: 16 bytes (with padding)

Quantity_t Structure (Standard Precision): 

typedef struct Quantity_t {
    uint64_t raw;       // 8 bytes - fixed-point integer
    uint8_t precision;  // 1 byte - decimal precision
    // Padding: 7 bytes (aligned to 8-byte boundary)
} Quantity_t;  // Total: 16 bytes (with padding)

BarType_t Structure: 

typedef struct BarType_t {
    InstrumentId_t instrument_id;  // ~50-100 bytes (symbol + venue strings)
    BarSpecification_t spec;        // ~20 bytes (step, aggregation, price_type)
    AggregationSource source;       // 1 byte (enum)
    // Padding and alignment
} BarType_t;  // Total: ~80-120 bytes (variable, depends on strings)

Bar_t Structure: 

typedef struct Bar_t {
    BarType_t bar_type;    // ~80-120 bytes
    Price_t open;          // 16 bytes
    Price_t high;          // 16 bytes
    Price_t low;           // 16 bytes
    Price_t close;         // 16 bytes
    Quantity_t volume;     // 16 bytes
    uint64_t ts_event;     // 8 bytes
    uint64_t ts_init;      // 8 bytes
} Bar_t;  // Total: ~176-216 bytes (depending on BarType_t size)

Cython Bar Class

cdef class Bar(Data):
    cdef Bar_t _mem        # Embedded C struct (176-216 bytes)
    cdef readonly bint is_revision  # 1 byte (Python bool)

    # Python object overhead: ~48 bytes (PyObject header)
    # Total per Bar object: ~225-265 bytes

Memory Views (Zero-Copy)

double[:] Memory View: - Points directly to numpy array's underlying buffer - No memory copy - Zero overhead for accessing data - Lifetime: tied to numpy array

uint64_t[:] Memory View: - Points directly to numpy array's underlying buffer - No memory copy - Zero overhead for accessing data - Lifetime: tied to numpy array

Memory Ownership and Transfer

Memory Sizes (Standard Precision Mode)

Configuration Constants: - PRECISION_BYTES = 8 (64-bit integers for prices/quantities) - FIXED_SCALAR = 1_000_000_000.0 (10^9)

Per Bar Memory Footprint (10,000 bars example):

Stage Components Size per Bar Total (10K) Ownership Lifetime
DataFrame Data (5×float64) + index + overhead ~250-350 bytes ~2.5-3.5 MB Python heap Until GC
Memory Views double[:] (5 cols) + uint64_t[:] (2 timestamps) 56 bytes 560 KB Zero-copy (views) Tied to DataFrame
C Struct (Bar_t) BarType_t + 4×Price_t + Quantity_t + 2×uint64_t ~176-216 bytes ~1.8-2.2 MB Python heap (embedded) Same as Bar object
Bar Object PyObject header + Bar_t _mem + flags ~225-265 bytes ~2.25-2.65 MB Python heap Until GC
Temporary ts_inits array (computed) 8 bytes ~80 KB Python heap During processing

Memory Transfer:

Transfer Amount Method Zero-Copy
DataFrame → Views 0 bytes Direct pointer access Yes
Views → C Structs ~176-216 bytes/bar FFI function calls No (extracted/converted)
C Structs → Bar Objects 0 bytes Embedded in Python object Yes

Memory Lifecycle

1. Python: DataFrame created (2.5-3.5 MB)
   ↓
2. Cython: Memory views created (0 bytes - zero-copy)
   [DataFrame still in memory]
   ↓
3. Cython: Process each row via map()
   [For each row:]
   ↓
4. Cython: Extract values from memory views (stack operations)
   ↓
5. Rust FFI: Create Price_t, Quantity_t structs (stack)
   ↓
6. Rust FFI: Create Bar_t struct (~176-216 bytes)
   ↓
7. Cython: Create Bar Python object (~225-265 bytes)
   [Bar_t embedded in Bar._mem]
   ↓
8. Python: list[Bar] returned
   [DataFrame can be GC'd, but Bar objects remain]

Key Points: - Zero-copy views: double[:] and uint64_t[:] provide direct numpy array access (no copy) - C struct embedding: Each Bar object contains embedded Bar_t struct on Python heap - Peak memory: ~6.15 MB (DataFrame + Bar objects) vs ~7.7 MB for Arrow approach - Efficiency: Row-by-row processing, no intermediate serialization, compact C structs (~176-216 bytes vs ~250-350 bytes in DataFrame)

Cython Implementation Details

BarDataWrangler Class

cdef class BarDataWrangler:
    cdef BarType bar_type
    cdef Instrument instrument

    def process(self, data: pd.DataFrame, ...):
        # 1. Normalize DataFrame index
        data = as_utc_index(data)

        # 2. Add default volume if missing
        if "volume" not in data:
            data["volume"] = float(default_volume)

        # 3. Convert timestamps (zero-copy views)
        ts_events, ts_inits = prepare_event_and_init_timestamps(
            data.index, 
            ts_init_delta
        )
        # ts_events: uint64_t[:] - zero-copy view
        # ts_inits: uint64_t[:] - new array (computed)

        # 4. Process each row (zero-copy access)
        return list(map(
            self._build_bar,
            data.values,    # double[:] - zero-copy view
            ts_events,      # uint64_t[:] - zero-copy view
            ts_inits        # uint64_t[:] - new array
        ))

    cpdef Bar _build_bar(
        self, 
        double[:] values,      # Zero-copy view: [open, high, low, close, volume]
        uint64_t ts_event,     # Single value
        uint64_t ts_init       # Single value
    ):
        # Extract values from memory view (no copy)
        # Create Price/Quantity objects (calls Rust FFI)
        # Create Bar object (embeds C struct)
        return Bar(
            bar_type=self.bar_type,
            open=Price(values[0], self.instrument.price_precision),
            high=Price(values[1], self.instrument.price_precision),
            low=Price(values[2], self.instrument.price_precision),
            close=Price(values[3], self.instrument.price_precision),
            volume=Quantity(values[4], self.instrument.size_precision),
            ts_event=ts_event,
            ts_init=ts_init,
        )

Timestamp Processing

def prepare_event_and_init_timestamps(
    index: pd.DatetimeIndex,
    ts_init_delta: int,
):
    # Convert DatetimeIndex to uint64 view (zero-copy)
    ts_events = index.view(np.uint64)  # Zero-copy view

    # Compute ts_inits (new array created)
    ts_inits = ts_events + ts_init_delta  # New numpy array

    return ts_events, ts_inits

Memory Impact: - ts_events: 0 bytes (zero-copy view of index) - ts_inits: ~80 KB for 10,000 bars (new array: 10,000 × 8 bytes)

Price and Quantity Creation

cdef class Price:
    cdef Price_t _mem  # Embedded C struct

    def __init__(self, double value, uint8_t precision):
        # Convert float to fixed-point integer
        # Calls Rust FFI: price_new(raw_value, precision)
        self._mem = price_new(value, precision)

Memory Impact: - Price object: ~64 bytes (PyObject header + Price_t struct) - Created temporarily during Bar construction - Can be garbage collected after Bar is created (if not referenced)

Performance Characteristics

Advantages

  1. Zero-Copy Memory Views: Direct access to numpy arrays without copying
  2. Efficient Row Processing: Process one row at a time, minimal memory overhead
  3. Direct C Structs: No intermediate serialization format
  4. Python Integration: Bar objects are native Python objects
  5. Memory Efficient: Lower peak memory than Arrow approach for single-pass

Disadvantages

  1. No Batch Processing: Must process row-by-row
  2. No Streaming: Cannot process data in chunks easily
  3. Python GIL: Processing happens with GIL held (single-threaded)
  4. No Cross-Language Interop: Cython objects are Python-specific
  5. Memory Views Lifetime: Must keep DataFrame in memory during processing

Comparison: Cython vs Arrow

Aspect Cython Approach Arrow Approach
Memory Views Zero-copy (double[:]) Arrow IPC bytes (copied)
Processing Row-by-row Batch processing
Peak Memory ~6.15 MB (10K bars) ~7.7 MB (10K bars)
Streaming No Yes
Cross-Language Python only Python, Rust, others
Serialization Direct C structs Arrow IPC format
GIL Impact Held during processing Released in Rust
Batch Operations No Yes (columnar)

Usage Example

from nautilus_trader.persistence.wranglers import BarDataWrangler
from nautilus_trader.model.data import BarType
from nautilus_trader.test_kit.providers import TestDataProvider, TestInstrumentProvider

# 1. Create instrument
instrument = TestInstrumentProvider.default_fx_ccy("GBP/USD")

# 2. Create wrangler
wrangler = BarDataWrangler(
    bar_type=BarType.from_str("GBP/USD.SIM-1-MINUTE-BID-EXTERNAL"),
    instrument=instrument,
)

# 3. Load CSV data
provider = TestDataProvider()
df = provider.read_csv_bars("fxcm/gbpusd-m1-bid-2012.csv")

# 4. Process DataFrame (zero-copy memory views used internally)
bars = wrangler.process(
    data=df,
    default_volume=1_000_000.0,
    ts_init_delta=0,
)

# 5. Use Bar objects
for bar in bars:
    print(f"{bar.ts_event}: {bar.open} - {bar.close}")

Memory Optimization Tips

  1. Process in Chunks: For very large datasets, process DataFrame in chunks 

    chunk_size = 10_000
all_bars = []
for i in range(0, len(df), chunk_size):
    chunk = df.iloc[i:i+chunk_size]
    bars = wrangler.process(chunk)
    all_bars.extend(bars)
    # DataFrame chunk can be GC'd here

  2. Reuse Wrangler: Create wrangler once and reuse for multiple DataFrames

  3. Release DataFrame Early: After processing, explicitly delete DataFrame 

    bars = wrangler.process(df)
del df  # Allow GC to free DataFrame memory

  4. Use Memory Views Directly: For advanced use cases, work with memory views directly in Cython

  5. Batch Processing: Consider Arrow approach for very large datasets or streaming scenarios
